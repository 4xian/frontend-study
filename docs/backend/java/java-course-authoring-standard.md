# Java 课程编写标准

> 版本：v1.3
> 状态：已确认
> 确认日期：2026-08-16
> 适用范围：`src/categories/backend/java/**/learn/*.md`
> 内容基准：[`java-course-content-sample.md`](./java-course-content-sample.md)

本标准记录 Java 学习课程已经确认的编写方式。后续每课的格式、解释密度和示例完整度不得低于
“变量与赋值”示例，但不能机械复制示例的章节名称或句式。课程应像自然展开的教学内容，而不是
调研报告、实施计划或固定问答模板。

本标准是后续 Java 课程编排与正文开发的唯一内容规范。仓库中已有的 `dzzz-app` 计划、审计、研究和
signoff 资料保留备用，但不参与新课程的选题、顺序、示例设计、前置关系或完成状态判断。

课程接入继续使用模块的显式 `entry-manifest.ts` 和 Track。新增 Markdown 后同步稳定 ID、slug、课程
顺序、状态与正文 loader；不扫描目录，也不手工维护额外的 JSON 索引。Catalog 元数据索引由开发和生产
共同使用的 Markdown 插件自动生成，浏览器只在打开详情时加载该课程的 `?content-entry` 正文。生产构建
仍会完整解析所有已登记正文进行发布校验，因此不能把“索引可生成”当作正文验证通过。

## 一、课程边界

### 1. 一课对应一项可独立掌握的能力

课程粒度以“学习者完成后能独立使用的一项能力”为准，不能把多个需要分别学习的主题塞进同一课，
也不能把一个完整能力拆成只有定义或一条语法的碎片。

课程可以讲清当前知识点必需的相关内容，包括运行或编译机制、使用边界、相邻概念区别和工程影响。
这些拓展必须帮助学习者真正掌握本课能力，不能为了增加篇幅扩张成百科。

### 2. 严格遵守学习顺序

当前 Spring Boot Web 路线的选题、前置关系和左侧课程顺序，必须以
[`spring-boot-web-curriculum-plan.md`](./spring-boot-web-curriculum-plan.md) 的 104 课最终课程表为唯一顺序源。
本标准负责正文格式和内容质量，课程计划负责课程边界和排列顺序，两者不得相互替代。

新路线实施期间可以暂时保留旧课程，但将旧课程过滤后，Track 中已接入的新课程相对顺序必须与
104 课课程表完全一致。新课程必须插入计划规定的位置，不得按编写时间追加到当前课程末尾，也不得因复用
旧稳定 ID、slug、页面地址或旧阶段分组而保留错误顺序。尚未编写的课程不要为了占位提前标记为 `available`。

正文默认只使用前置课程已经讲过的能力。确实需要提前出现少量后续知识时，应保持示例可理解；基础
语法不必反复标注，独立且重要的后续主题可以简短指出对应课程，不在当前课提前完整讲授。

### 3. 教学正文只保留学习内容

正文不得出现阶段编号、批次编号、Gate、调研过程、计划状态、实施记录、审查结论或本地项目计划。
标题必须简短、准确，直接表达本课或本节知识点，不添加“带你学会”“从零精通”等冗余文字。

## 二、版本与研究

### 1. 以 JDK 25 为教学主线

所有新课默认使用 JDK 25 的语言规则、标准库和工具行为。Java 8 只在当前小知识点存在真实差异时
就近说明，并给出能够使用的 Java 8 写法；没有差异时不增加版本对比。课程不涉及 JDK 26。

版本规则不能只凭 Java 8 时代的记忆推断。若 JDK 25 已交付语言变化，必须回到对应 JEP 或 Java 25
官方语言指南核验后再写正文。例如 JEP 513 允许在显式 `super(...)` 或 `this(...)` 前放置不读取当前对象、
不调用其实例方法且不访问 `super` 实例成员的安全语句；简单赋值给本类声明且没有初始化器的字段是一个明确
例外。Java 8 仍要求构造器调用为第一句。两版课程若采用传统兼容写法，应明确这是兼容选择，同时把真实
差异放在对应易错项和验证反馈中。

声称某个语法或 API 是 JDK 25 与 Java 8 的差异前，还必须核验它的实际引入版本。已经在 Java 8 可用的能力
不得为了制造对照而改写成更冗长形式，例如菱形运算符从 Java 7 已可用，Java 8 代码不需要机械展开
`new HashMap<>()` 的泛型参数。两版差异应由对应编译器反馈或官方版本资料证明。

两版源码表面相同或都能编译时，还必须核对警告和可观察语义，不能只记录退出码。例如单个 `_` 在 Java 8
中仍是可读取的普通标识符，编译器会给出警告；Java 9 将其移除，JDK 22 又以不可读取的未命名变量语义重新
支持。此类差异应分别验证编译诊断和参数能否实际读取，再决定正文如何描述兼容写法。

兼容实现替换现代 API 时还必须验证语义范围，而不只验证常见输入。例如 `String.isBlank()` 按 Unicode code
point 使用 `Character.isWhitespace`，Java 8 的 `trim().isEmpty()` 不能表达完全相同的空白合同；若正文要求
两版等价，应提供 Java 8 辅助方法，并用非 ASCII 空白输入复现两版结果。

后续课程复用前置课的 record 数据合同时也适用同一原则：如果正文声称 Java 8 版本等价，必须同步实现前置课
已经教过的 `equals`、`hashCode`、`toString` 或其他可观察合同；如果当前示例只需要字段读取，应明确限定为
“本示例所需的固定数据对象”，不能把缺少对象合同的普通类描述成 record 的完整等价实现。

新课程不以任何本地项目为教学基准。Java 8 的通用兼容环境和旧项目维护能力可以在后续课程表中安排
独立课程，但内容仍以公开语言规则和可复现的中性示例为依据。

### 2. 每课编写前完成针对性调研

每课开始编写前必须围绕本课目标分别完成官方资料和社区资料检索。检索范围必须覆盖本课的核心规则、
正常用法、版本差异、主要边界、常见错误和工程使用技巧，不能只查询课程标题或只读取一篇概述。

官方规范、Javadoc、OpenJDK、JEP、Spring 官方文档和其他技术官方文档用于确认语言规则、API 合同、
版本差异和编译或运行行为。优先使用与当前教学版本直接对应的原始页面，不使用搜索摘要、转载文章或
聚合页替代原始来源。

社区检索用于发现官方文档通常不会集中列出的教学难点、真实误用、排错经验和工程技巧。候选来源包括
GitHub 仓库源码与测试、Issue、Discussion、维护者答复、Stack Overflow 问答和具有明确作者、日期、
适用版本及可复现示例的技术文章。转载、无来源结论、版本不明示例和无法复现的经验不能进入课程。

社区检索是每课必做步骤，但社区内容不是每课必备内容。没有找到正确、真实且能增加教学价值的社区
补充时，不得为了凑数量引用社区来源。社区候选中的关键技术结论必须回到官方合同核验，或通过临时
可执行示例复现；与官方规则冲突且无法解释的内容不得采用。

候选 URL 写入 `sources` 前必须再次核对页面标题、URL 和正文结论。已知 URL 返回 404 或已经迁移时，
必须找到官方 canonical 页面并替换，找不到就删除该来源及其无支撑结论。社区站点返回 403 时不能直接
判定页面失效；可以使用当前顺位的搜索服务或正文提取工具确认页面仍存在且内容相符，并记录其只作为
社区补充。搜索摘要只能帮助定位和核对可访问性，最终技术结论仍由官方原始页面或可复现验证支撑。

并行提交多条搜索请求时，单条超时不等于整批结果都不可用。应分别记录每条请求的成功或失败状态，保留
已经返回的可靠候选，只重试缺失主题；只有当前搜索服务对该主题仍无法给出可靠结果时，才按规定顺序切换
下一服务。社区候选只有标题和搜索摘要、正文提取为空时，不得把摘要写入课程结论；应在当前服务重试全文
提取，仍失败后再用下一顺位工具核对页面正文与答案上下文。

### 3. 调研材料只作临时工作稿

需要记录候选资料时，在 `/tmp` 下使用独立临时目录保存当前课程的研究稿。研究稿可以记录候选 URL、
来源类别、适用版本、候选结论、是否采用和核验方式，但不得写入仓库。课程完成后删除临时研究稿，
不保留调研报告、审查文档、Gate、signoff 或其他完成证明。

调研过程不进入学习正文。只有实际支撑最终正文的来源才维护在 frontmatter `sources` 中；检索过但
未采用的候选不进入课程，也不为了证明检索过程而长期保存。

### 4. 旧课程只作为可复核素材

编写当前课程前，可以查看仓库中主题相近的旧课程，提取可能复用的知识解释、示例思路、易错情况和
版本差异。旧课程不是当前路线的权威来源，也不代表其中内容仍然正确；实际采用的技术结论仍必须使用
本课重新检索的官方资料或可信社区资料核验，并在最终 `sources` 中记录真实外部来源。

复用前必须先根据当前课程的能力边界、前置关系和学习目标列出本课需要讲清的知识点，再把旧课程、其他
课程、已有正文或本地素材中的候选内容逐项映射到这份清单。不能因为某个来源已经写过某个主题，就默认
它的知识范围、解释深度、示例、易错项或
版本信息足够当前课程使用。每个候选都必须重新确认：技术结论是否仍然正确、覆盖范围是否完整、解释
是否达到当前课程需要的深度、示例能否支撑目标能力，以及 JDK 25 主线和真实 Java 8 差异是否已经处理。

复用内容即使全部正确，只要不能覆盖当前课程的一项目标能力、关键边界、主要错误或完整实践，就仍然
属于内容缺口。此时必须围绕缺失主题继续检索官方资料和社区资料，回到官方原始页面核验技术结论，并用
必要的临时示例复现行为；补足后才能写入正文。不得为了提高旧内容复用率而缩小课程目标、跳过必要知识，
也不得用旧课篇幅、旧来源数量或已有示例数量证明当前课程已经完整。

可以复用的是经过核验的知识内容，不能直接复用旧课程的章节结构、固定句式、计划编号、项目调研、
审查信息或旧版完成状态。旧课程即使已经存在，也不能代替当前课程按本规范重新编写和完成。

这里的“复用”只允许发生在内容层：可以重新表达经过核验的概念、规则、示例意图、错误现象和版本事实；
不得复制旧课或其他课程的章节骨架、标题顺序、固定问答标签、段落模板、directive 排布、练习结构或小结
句式。页面地址、稳定 ID、slug、manifest 和 Track 可以在身份未变化时继续使用，但正文必须根据当前课的
能力边界和现行成品格式重新组织。发现正文仍以“为什么需要学习 / 学习目标 / 前置术语 / 零基础知识点
详解 / 如何使用 / 性能注意 / 如何验证”等通用旧模板串联，或逐点重复“它是什么 / 有什么作用 / 什么时候
使用 / 怎么使用”时，应判定为未按当前规范编写，直接重写正文结构，不能只替换标题或删除旧编号。

新路线实施期间不得提前删除旧课程。只有 104 门新课程全部完成，并确认旧课程不再被 manifest、学习
路线、前置关系、关联课程或 Demo 引用后，才能集中清理旧课程正文和对应的过时课程配置。`dzzz-app`
资料和审计材料不属于这次旧课程清理范围，继续保留备用。

## 三、课程元数据

### 1. 保留运行时需要的最小字段

每课 frontmatter 以已确认示例为准，必须包含稳定身份、页面摘要、学习阶段、前置课程、学习目标、
小结、标签、适用版本、核验日期和实际使用的来源。每个新来源都必须使用 `sourceOrigin` 标明
`official` 或 `community`。普通 Java 课程至少维护：

```text
id、type、title、summary、domain、technology、module、stage、level、estimatedMinutes、
prerequisites、objectives、recap、related、tags、appliesTo、verifiedAt、sources
```

来源条目的写法如下：

```yaml
sources:
  - id: jls-25-variables
    title: Java Language Specification 25 - Types, Values, and Variables
    url: https://docs.oracle.com/javase/specs/jls/se25/html/jls-4.html
    sourceOrigin: official
    sourceType: specification
    appliesTo: Java SE 25
    claims:
      - 变量、变量类型、基本类型值与引用值的语言规则
```

`sourceType` 只能使用仓库 frontmatter schema 已注册的枚举值：`specification`、`api-doc`、
`official-reference`、`release-note`、`source-code`、`official-test`、`security-standard`、
`static-analysis`、`engineering-reference` 和 `project-source`。来源类别不匹配时应选择最接近的已注册值，
不能在课程中临时创造新枚举；提交前必须执行真实的 frontmatter 内容解析，不能只依赖 TypeScript 检查。

`sourceOrigin: official` 表示技术规范、官方文档、官方源码、官方测试或项目维护方正式材料；
`sourceOrigin: community` 表示社区文章、问答、讨论或非官方仓库示例。GitHub URL 不能仅凭域名判断，
必须根据仓库或讨论的实际维护者确定来源类别。`claims` 只记录该来源实际支撑的正文结论。

新课程不使用 `modernBaseline`、`legacyBaseline` 和 `projectEvidence`，也不为了生成“课程依据”区域
补充这些字段。适用版本由 `appliesTo` 表达，真实差异直接在对应知识点中说明。

frontmatter 必须同时保留开头和结尾的 `---` 分隔符。缺少结尾分隔符时，正文可能被继续当作 YAML，文本
检查与 TypeScript 检查都不足以证明课程可加载；编辑后必须通过真实 `*.md?content-entry` 路径解析一次。

### 2. 元数据不进入教学叙事

`sources` 用于支撑语言规则、版本差异、API 行为和实际采用的社区补充，不在正文重复生成“课程依据”
“参考资料”或调研过程。页面来源列表必须能够明确显示“官方资料”或“社区补充”。学习目标与小结由
页面现有能力展示，正文从课程问题和知识内容直接开始。

## 四、正文结构

### 1. 标题编号

- 一级标题不编号，只写简短课名。
- 根级二级标题使用中文序号：`一、`、`二、`、`三、`。
- 表示知识小点的根级三级标题，在每个二级标题下从 `1.` 重新编号。
- 当前正文解析器只接受二级和三级标题，不使用四级标题。三级标题下确需继续细分时，使用
  `（1）`、`（2）`、`（3）`编号的加粗段首或列表表达从属关系，并在每个三级标题下重新编号。
- 只承担分组作用、且内部项目已经编号的容器标题不编号，例如“六个典型错误”。
- `pitfalls`、`compare`、`exercise` 等 directive 内部标题不手工编号，由内容组件负责其展示层级。

正文开头使用少量自然段建立问题和本课学习范围，不单独堆砌“课程依据”或计划说明。

### 2. 章节按知识递进组织

章节名称必须根据本课主题确定，不强制使用“它是什么、有什么作用、如何使用”等固定小标题。内容
通常按以下学习过程展开，但可以根据知识点调整合并：

1. 建立最小概念和准确心智模型。
2. 讲清核心语法、API 或操作方式。
3. 解释编译、执行、状态变化或数据流。
4. 补充现代写法、边界和相邻概念区别。
5. 集中处理经过调研确认的易错情况。
6. 使用完整程序串联本课能力。
7. 通过练习、完整参考实现和运行结果完成自检。

“变量与赋值”示例中的八章是已经确认的成品结构，不是要求所有课程照抄八个同名章节。后续课程应
保持相同的教学完整度，并让读者能够从章节标题直接判断当前正在学习什么。

## 五、知识点深度

### 1. 同时覆盖宽度和深度

每个重要知识小点应根据实际需要覆盖以下内容：

- 准确含义以及它和相邻概念的区别。
- 语法、API 或命令各组成部分的职责。
- 编译器、JVM、框架或数据流实际经历的关键过程。
- 正常使用条件、边界条件和不适用场景。
- 从最小写法到稍完整场景的递进示例。
- 输出、返回值、编译结果或状态变化，以及产生该结果的原因。
- 能帮助理解本课的进一步机制或工程影响。
- 当前知识点存在时的 Java 8 差异。

不能只完成标题表面的定义和一段代码就判定知识点完成。也不能为了套格式，逐点重复“是什么、有什么
作用、如何使用”这些标签；上述内容应自然融入解释、代码、结果和对比中。

### 2. 深度必须服务当前能力

宽度不是罗列更多名词，深度也不是提前引入高级主题。加入的每一段都应帮助学习者解释行为、正确
使用、判断边界或排查错误。一个相关主题已经能形成独立能力时，应拆到它自己的课程。

## 六、示例与易错内容

### 1. 每个重要小点都有可观察示例

涉及语法、API、配置或命令时，必须给出能独立理解的代码或操作示例，并说明预期结果和原因。需要
运行的 Java 示例应提供完整类和入口；只展示局部规则时可以使用最小片段，但必须明确其上下文。

Java 方法和构造器定义上方使用规范的中文 Javadoc。示例不得依赖尚未学习的大型框架、抽象或第三方
库，也不得使用真实凭据和业务敏感数据。

讲解名称相近但语法约束不同的形式时，标题、解释和代码必须逐项对齐。例如 record 的完整 canonical
constructor 带有与 header 对应的参数列表并显式赋组件字段，compact canonical constructor 省略参数列表且
不能直接给组件字段赋值。此类对照应分别编译最小示例，不能只凭术语检查判断正文正确。

从协议或语言规范转写语法产生式时，必须保留方括号等可选标记，并逐项核对它与相邻自然语言解释一致。
不能一边把某个组成部分写成必选，一边又在正文说明它可以省略；修正后应重新执行内容解析和技术复核。

### 2. 易错示例覆盖主要学习风险

易错项不强制凑固定数量，但必须覆盖调研和本地验证发现的主要错误。每个易错项根据实际情况说明：

- 现象和触发条件。
- 语言、API 或执行机制层面的原因。
- 编译、运行、数据或维护后果。
- 能直接对照的错误代码和正确代码。
- 影响版本和可重复的验证方式。

错误示例集中放在 `pitfalls` 或 `compare` 中。易错章节的容器标题不再重复编号，组件内部的每个错误
项目保持独立序号。

### 3. 社区补充必须显式标记

社区资料只是帮助发现问题，不能代替官方规则。正文中只有社区独有的工程技巧、排错经验或使用建议
需要在段落开头使用醒目的 `**社区补充：**` 标记，并在 `sources` 中保留对应的
`sourceOrigin: community` 来源。由社区线索发现、但已经回到官方资料确认的语言规则和 API 合同，按
官方内容正常讲解，不重复标记为社区观点。

社区补充必须说明适用版本、成立条件和核验结果，不能使用“大家都这样做”“最佳实践”等无法验证的
措辞。一个社区候选没有进入最终正文时，也不进入 `sources`。

课程使用 `:::pitfalls` 时必须遵守仓库解析器的固定字段合同：每个易错项至少提供“触发条件”“原因”“后果”
和“验证方式”，并用“错误示例”“正确写法”分别引出紧随其后的代码块。不得自行添加“错误操作”“正确操作”
等未注册字段；如需解释操作，应写入触发条件、代码示例或验证方式。提交前应先执行内容解析或构建检查，
确认字段和代码块均能被转换。

`pitfalls` 的代码块后也不能插入没有字段标签的普通说明段落；补充说明应并入前后相邻的已注册字段。构建若
报告 `pitfalls 不支持 AST 节点：paragraph`，应先定位并移除这类容器内的游离段落，再重跑真实内容构建。

`pitfalls` 需要“多个典型错误”等分组标题时，标题必须放在 `:::pitfalls` 之前。容器内的第一个三级标题会
被解析为第一条易错项，不能拿来充当容器标题；否则构建会把它判定为缺少触发条件、原因、后果、两段代码或
验证方式。修正标题位置后必须重跑真实内容加载，不能只用文本搜索确认字段似乎存在。

同一章节的多个相邻易错项应放进一个 `:::pitfalls` 容器，每项以自己的三级标题开始。把每项分别包进独立
容器虽然能通过解析，却会生成多个易错面板并让组件内序号重复从一开始；修正后应通过真实 loader 同时断言
`pitfalls` 块数量和块内 `items` 数量，不能只统计 Markdown 中的三级标题。

`**社区补充：**` 也不能作为 `pitfalls` 容器内的独立段落；解析器会把它当成未注册字段并报告“未知字段：
社区补充”。需要为易错章节提供社区背景时，把完整标记段落放在 `:::pitfalls` 之前，再让容器内各项只使用
固定字段。修正后必须重跑同一真实 Markdown loader。

`compare` 容器的两个内部标题必须逐字匹配 directive 属性，例如 `before="Java 8" after="JDK 25"` 对应
“Java 8”和“JDK 25”。每个标题后只能紧跟一个带语言的代码块，容器内不接受解释段落；限定语和版本说明
应放在容器外。文本结构看似正确也不能代替解析器合同，修改后必须从真实 `*.md?content-entry` 路径重新加载。

## 七、完整示例与练习

### 1. 每课末尾提供完整程序

完整示例必须把本课前面讲过的主要能力连接起来，说明要解决的问题、给出完整可运行代码、展示运行
结果，并解释关键状态或执行过程。它不能只是把前面的最小片段原样拼接。

课程沿用前置课工程时，必须先核对前置课已经创建的模块、包和文件：已有类应写成“打开并修改”，
只有新文件才写成“创建”，不能让学习者重复创建同名类。不同版本需要不同 POM 编译目标时，应使用
目录明确分开的独立工程，并同时写清 Project SDK、模块 SDK、Maven Runner JRE、POM 目标和 Reload
步骤，不能声称只切换 IDEA SDK 就完成版本迁移。

### 2. 练习必须可以独立验收

练习需要明确任务、约束和可观察的验收结果。练习后提供完整、可运行的参考实现及预期输出，不能只
给思路、局部代码或省略关键部分。Java 8 存在差异时，在练习对应位置说明必要修改。

如果验收要求学习者修改程序生成的文件后再次导入，参考实现必须提供不会先覆盖该文件的可运行入口，
并写清入口参数或操作步骤及预期失败消息。只能通过正文之外的临时探针调用内部方法，不算独立验收。

练习只能重组或加深本课已经允许的能力，不能为了制造新任务而增加正文明确排除的命令、API 或功能。
练习约束、参考实现和验收输入必须继续遵守同一课程边界；确实需要新能力时，应留给对应的后续课程。

`:::exercise` 必须以一个不手工编号的三级标题开始，容器内只允许“要求”“验收”或“完成标准”以及
可选的“参考答案”字段。“完成标准”与“验收”等价；字段值可以直接写在同一段，也可以让空标签紧跟
一个代码块。容器内不得直接放普通段落、额外标题、列表或没有字段标签的代码块。较长的完整参考实现
应放在 directive 之后的正常正文中。

同一个 exercise 字段不能先在标签同行写文字，再紧跟一个代码块；这种混合写法会让代码块脱离字段并报告
“exercise 包含未知字段或节点：code”。需要展示验收输出时，把解释并入“要求”，再让空的“验收”标签
直接承接代码块，或把代码块移到 directive 外。

正文中的命令、坐标、时间或标识符如果包含“ASCII 冒号 + 字母或数字”，必须把整个字面量放进反引号，
例如 `dependency:tree`、`09:30`。否则 remark-directive 可能把冒号后的内容解析为 `textDirective`，
导致真实 loader 报“不支持的行内 AST 节点”。普通段落按此规则处理；标题应改用自然语言，把完整字面量
放到标题后的正文，因为当前标题与目录转换会保留行内代码的反引号。修改后应重跑同一内容构建和页面验收，
确认 AST 与最终标题都正确。

Markdown 表格单元格中的管道符即使位于行内代码中，也必须写成 `\|`；例如逻辑或应写为
`` `\|\|` ``。否则 GFM 可能把运算符拆成新的列，内容构建会报告“表格每行列数必须一致”。修正后应
重跑真实内容构建，并确认页面仍显示未带反斜杠的运算符。

## 八、单课完成条件

一门课程只有同时满足以下条件才算完成：

- 课程主题、前置能力和边界清楚，没有混入独立课程。
- 已先列出当前课程所需知识点，再检查主题相近的旧课程；复用内容经过范围、深度、版本和示例审计，
  不足部分已经继续检索并补齐，没有沿用旧课程结构或完成状态。
- 已分别完成官方资料与社区资料的针对性检索；社区内容只在正确、真实且能增加教学价值时采用。
- 每个实际使用的来源都标明官方或社区类别，社区补充具有适用条件和核验结果。
- 正文达到已确认示例的解释密度，重要小点同时体现宽度与深度。
- JDK 25 主线完整，Java 8 差异只在确有差异的位置出现。
- 每个重要小点具有示例、结果和解释，主要易错情况具有错误与正确对照。
- 末尾具有完整示例、完整练习参考实现和运行结果。
- 正文没有计划、调研、批次、Gate 或本地实施信息。
- Markdown、代码、manifest、学习路线和页面展示完成当前课程所需的定向验证。
- `/tmp` 中的临时研究稿和临时验证文件已经删除，仓库中没有新增调研或审查文档。

课程正文每次新写入或修改后，必须先验证当前正在编写的那一课页面服务是否正常，再进行其他验证。验证目标
必须是本课的真实路由，而不是首页或其他课程；至少检查页面对应的 Markdown 模块请求、页面加载状态以及浏览器
控制台错误和警告。若出现 500、动态模块加载失败、解析错误、运行时异常或页面停留在加载状态，必须先修复并从
同一路由重新验证为零错误，再继续 Java fixture、内容 loader、类型检查、构建、布局和复审等后续步骤。服务健康
检查未通过时，不得用其他验证通过替代，也不得提前更新课程完成状态。

定向搜索 Markdown 字面量时要同时满足 shell 引号规则：`rg` 模式中只要包含反引号，就用单引号包裹整个
模式，避免 zsh 或 bash 把反引号解释为命令替换。需要匹配单引号时应改用固定字符串参数或安全转义，
不能为了省略引号而执行可能改变环境的命令。

`rg` 的搜索模式若以 `-` 或 `--` 开头，会被误当成命令选项并报 `unrecognized flag`。应把 `--glob` 等所有
真实选项放在前面，再用 `--` 结束选项解析，例如 `rg --glob '*.css' -- '--space-5' src`；`--` 之后的内容
都会按模式或路径处理，不能再追加选项。修正参数顺序后必须重跑原查询，不能把命令行解析错误当成零匹配。

命令参数中的 `*`、`?` 或方括号模式若希望交给 `rg --glob` 等工具处理，必须用单引号包裹；未加引号时，
zsh 会先尝试展开模式，没有匹配项便报 `no matches found`，目标工具实际上尚未运行。例如应写
`rg --glob '*.md' 'Lambda' src`，而不是把 `*.md` 裸写在命令中。出现该错误后应修正引号并重跑原命令，
不能把 shell 展开失败当成搜索无结果或仓库内容错误。

使用 `curl` 读取来源后再通过管道交给 `rg -m`、`head` 等会提前退出的消费者时，下游找到足够内容就会关闭
管道，仍在写入的 `curl` 可能以 `Failure writing output to destination` 和退出码 56 结束。这不能直接证明来源
页面失效；需要断言生产者成功时，应让下游完整读取响应，或先保存到 `/tmp` 独立文件后再定向搜索，然后从
原 URL 重新完成同一来源核验。

shell 命令不能在同一条简单命令中一边临时赋值、一边用 `$NAME` 展开该变量作为可执行路径；外层 shell
会在这次赋值生效前完成展开，结果可能把空字符串当成命令。应先在前一条命令中导出并核对变量，或直接
使用已经解析的绝对路径。出现 `permission denied` 且命令位置为空时，应先检查变量展开结果，再重跑原
验证流程，不能把验证器入口错误记成页面或课程失败。

验证命令需要把含 `$()`、反引号或多层引号的脚本传给 Docker 等子进程时，不得把脚本直接拼进外层
双引号命令。应使用 `apply_patch` 在 `/tmp` 创建最小脚本，再让目标进程直接执行；否则宿主 shell 可能
提前展开命令替换，产生与目标环境无关的失败，甚至执行了原本只应在容器内运行的命令。

通过 JavaScript 模板字符串生成临时 shell 脚本时，shell 的 `${name}` 也可能被外层 JavaScript 提前
插值；反过来，省略大括号写成 `$name_suffix` 又会被 shell 当作变量 `name_suffix`。这类成功标记或路径
应使用不会被外层解释的字符串拼接，生成后先检查脚本文本，再从头重跑完整反馈环，不能把验证器的变量
展开错误记成课程代码失败。

临时 JavaScript 验证器需要定位 Markdown 代码围栏时，不要把未转义的反引号直接拼进模板字符串或动态
正则。应使用字符码构造围栏标记并按起止位置提取，先让 Node 完成语法检查，再运行课程断言；解析阶段失败
说明验证器尚未读取课程，修正后必须从同一输入重跑完整反馈环。

临时验证脚本依赖环境变量、容器工作目录或挂载路径时，必须在脚本入口或同目录说明中记录完整调用合同，
并在执行前核对必需变量。面向 `/workspace` 等容器路径编写的脚本不能直接当作宿主脚本运行；缺少变量时
应判定为验证器调用错误，按正确 Docker 参数重跑后再判断课程结果，不能把入口失败记成课程代码失败。

临时 Java 验证脚本在调用 `javac -d` 前必须显式创建每一个源码、class 和日志输出目录；缺少目录会让编译器
在读取被测源码前直接失败。验证脚本入口失败时先修正目录合同，再从相同 JDK 和源码副本重跑完整反馈环。

通过 `apply_patch` 创建的临时 shell 脚本不一定带可执行权限；直接按路径调用若得到 `permission denied`，说明
被测源码尚未执行。应使用 `sh /tmp/.../script.sh` 显式调用，或先核对并设置最小执行权限，再从同一输入重跑，
不能把验证器入口权限错误记成课程编译失败。

临时验证脚本把构建输出重定向到日志时，失败路径必须回显相关日志或保留可立即读取的证据，不能只返回
非零退出码。对日志文本的断言应先从一次真实输出确认稳定字面量，再用于批量反馈环；断言本身失败时要
区分“被测内容失败”和“验证脚本预期写错”。

课程中的命令必须按正文记录的原样进入 fresh 环境反馈环。验证时不得擅自增加 `-am`、预先执行 `install`
或复用已经填充的本地仓库，再用这个更强条件证明正文命令可运行；确需增强命令时，应先同步修改正文和
解释，再从空缓存重跑。长命令返回后台会话 ID 只表示仍在运行，必须继续轮询到明确退出码，不能把空输出
或未定义退出码记为通过。

并行运行 Maven 容器时，不得让多个容器共享同一个尚未初始化的宿主缓存目录；镜像入口和 Maven 都可能
同时创建 settings、元数据或下载临时文件，导致与课程源码无关的竞争失败。首次初始化应按版本串行完成，
或为每个并行任务分配独立缓存。发生竞争后先确认相关容器全部退出，再从原始课程源码重新执行失败任务，
不能把缓存初始化错误记成编译失败，也不能用残缺缓存继续证明课程通过。

反馈环必须覆盖正文中学习者可复制执行的命令，包括主示例、完整练习和易错项的验证方式，不能只抽查主
流程。多模块 Maven 命令若要解析尚未安装的 reactor 依赖，必须从根目录选择目标模块并同时带上其依赖；
正文和验证脚本应使用同一条命令，不能依靠验证环境中残留的本地仓库产物掩盖缺失的模块选择参数。

易错示例的输入必须确定触发正文声称的失败，不能只让代码“看起来可能出错”。涉及索引、长度或边界时，
应先手算该组输入的每个实际索引，再运行错误版确认异常或错误结果；如果错误输入碰巧仍合法，应更换为能
稳定复现的最小输入，并同步修正正确写法、验证方式和预期结果。

易错项的正确示例必须能够直接支撑同一项的验证方式：验证文字要求观察状态变化、返回值或输出时，正确代码
必须实际执行对应行为并提供可读入口；不能只展示修复后的声明，却要求读者观察代码中没有发生的结果。若字段
仍是 `private`，应补充最小的公开观察方法，或把验证方式收窄为仅检查编译和构造成功。
同一易错项引用完整程序中的方法时，触发条件、错误代码、正确代码和验证方式必须使用一致的方法签名；预期
输出还必须逐字来自该实现的真实运行结果，不能混用前文最小示例中同名但参数或输出不同的方法。

易错项的正确代码必须覆盖验证方式声明的全部输入分支。例如验证同时要求“有分隔符时正确拆分”和“无分隔符
时返回空结果”，代码就必须显式处理未找到分隔符的返回值，不能只给会在该分支抛异常的常见路径写法。

一个易错项不得合并两个独立故障后只为其中一个提供代码对照。若触发条件、原因或验证方式涉及不同机制，
应拆成独立项目；不属于当前课程核心风险的故障应删除，不能靠同一个标题或一段验证文字代替完整示例。

临时反馈源码还必须保持与正文相同的职责分布，不能把正文漏掉的校验、转换或状态更新偷偷放进另一个辅助
方法，使验证结果看似成立。例如正文声称服务方法先校验参数，反馈源码就必须由同一服务方法显式调用校验
方法，不能改成由数据读取方法代为校验。发现职责不一致时，应先修正文，再用同形源码重跑反馈环。

临时 Node/Vite ESM 验证脚本应保存在 `/tmp`，但必须从仓库根目录通过标准输入执行，或使用明确的仓库模块
绝对路径；否则 Node 可能以 `/tmp` 脚本位置作为包解析基准，找不到仓库依赖而产生与内容无关的假失败。
同一轮需要读取课程、manifest 和 Track 时应复用一个 Vite server 并顺序加载；不需要浏览器热更新时将
`server.hmr` 设为 `false`，并在 `finally` 中关闭实例，避免并行实例争用 HMR 或 DevTools 端口。
关闭 HMR 的浏览器验证服务会继续复用已经转换的 Markdown 模块；正文编辑后仅执行浏览器 `reload`，仍可能
显示旧模块内容。修改课程后应关闭并重新创建 Vite server，再用新的 Playwright 会话从目标 URL 重跑；不能用
旧页面中缺少新文本的结果判断编辑未生效，也不能把缓存快照当作最终验收证据。
检查 Markdown `ContentEntry` 时，稳定身份和正文分别从 `entry.meta.id`、`entry.meta.title` 与
`entry.blocks` 读取；Catalog 路线仍使用稳定 `entryId`，不能臆测不存在的顶层 `id` 或 `content` 字段。
课程来源同样位于 `entry.meta.sources`，不是顶层 `entry.sources`；来源数量与 `sourceOrigin` 断言必须按
真实元数据层级读取，不能让验证器的字段假设覆盖已经成功的正文解析结果。
必须通过 Vite 的模块加载器请求真实 `*.md?content-entry`；不要用裸 Node 直接导入
`build/markdown-plugin.ts`，否则 TypeScript 扩展名与项目模块解析环境缺失会在读取 Markdown 前产生假失败。
使用编程式 Vite server 执行只读内容探针时，必须覆盖
`optimizeDeps: { noDiscovery: true, include: [] }`，并把 `cacheDir` 明确指向本课 `/tmp` 临时目录。只设置
禁用依赖发现仍可能在仓库 Vite 配置变化时重建正式依赖缓存。直接沿用开发配置可能在
`node_modules/.vite/deps_temp_*` 写入依赖预构建缓存；一旦发生，应先精确删除本次新建的临时目录，再用禁用
依赖发现的同一 loader 重跑，不能把生成缓存留在工作区或把首次解析结果当成最终证据。
断言导出结构前先检查真实键名，当前正文块、练习和回顾分别使用 `entry.blocks`、`entry.exercises` 与
`entry.recap`，不能臆测不存在的 `entry.sections`，也不能把回顾误读成 `entry.meta.recap`。
读取学习路线时同样先按真实对象层级遍历；当前 `LearningTrackManifest` 使用
`track.stages -> stage.categories -> category.entries`，不能臆测 `stage.groups` 或其他未存在的字段，
否则会在课程断言前让验证器失败。修正结构假设后，必须从同一 Vite 快照重跑完整 loader 反馈环。
读取 manifest 或 Track 模块前还应先核对真实导出名；当前模块分别导出 `javaCoreContentEntries` 与
`backendJavaTrackManifest`，不能臆测 `backendJavaManifest`、`backendJavaTrack` 等不存在的包装对象。
验证器若在课程断言前报 `undefined`，先打印模块键并修正脚本，再从同一快照重跑。

全站内容被范围外文件阻塞时，可以在 `/tmp` 建立只导入当前 Markdown 与真实 `ContentRenderer` 的最小
Vite 页面壳。Vite CLI 的项目根目录使用位置参数，不写成不存在的 `--root` 选项；优先复用仓库现有
`vite.config.ts`，不要在临时配置中再次导入 Vite 内部 `dist/node` 模块。临时页面目录还必须通过符号链接
或等效的模块解析配置访问仓库 `node_modules`，否则依赖扫描会把 `vue` 等已安装依赖误报为缺失。页面壳
若直接从独立 `/tmp` 配置导入仓库 ESM Markdown 插件，Vite 默认的 `bundle` 配置加载器可能重新打包依赖并报
`Expected usable value but received an empty preset`；这是配置互操作假失败，不是课程解析失败。应改为复用
仓库配置，并用 `--configLoader runner` 启动同一临时壳，再从原 URL 重跑完整反馈环。
当前 Markdown 插件默认以 Vite 服务进程的 `process.cwd()` 解析仓库根，因此服务命令必须从仓库根目录执行，
并把独立 `/tmp` 页面目录作为 Vite 的位置参数；如果从 `/tmp` 直接启动，Markdown 请求可能返回 200 却仍是
以 `---` 开头的原始文本，浏览器随后报 `Invalid left-hand side expression in prefix operation`。应先检查转换响应，
修正服务工作目录后用新会话重跑，不能把原始 Markdown 的 JavaScript 语法错误记成课程内容失败。
验证至少核对桌面与 390px 视口、整页横向溢出、控制台错误、课程末尾，以及本课使用的 directive 组件。
临时入口应通过裸 `vue` 导入复用该 `node_modules` 中的同一份 Vue，不能一边绝对导入 `vue/dist`，一边让
真实组件解析裸 `vue`；两份运行时会产生 `resolveComponent can only be used in render() or setup()` 等验证壳
警告，不能据此判定课程页面失败。macOS 的 `/tmp` 可能解析为 `/private/tmp`，把临时目录交给 Vite 或
Rolldown 作为项目根时应先使用物理路径；逻辑路径与真实路径混用会让输出文件名错误地包含
`../../private/tmp`，应修正根目录后重跑，而不是修改课程内容。
最小页面壳还应声明真实 favicon 或 `data:` favicon；否则浏览器会自动请求 `/favicon.ico` 并产生 404，污染
“控制台零错误”证据。应修正临时壳并用新会话重跑，不得过滤该错误后直接把页面记为通过。

需要把生产构建输出定向到 `/tmp` 时，先核对 `package.json` 的脚本转发方式。当前 `npm run build` 外层使用
并行包装，直接追加拆开的 `--outDir /tmp/...` 可能让 npm 吞掉选项、只把路径传给 Vite，进而把临时目录
误当项目根目录并报告找不到 `index.html`。应先单独通过 `npm run type-check`，再执行
`npm run build-only -- --outDir /tmp/...`；只有从仓库根目录完成真实模块转换后，才能把结果记为生产构建证据。

使用 `playwright-cli eval` 做页面断言时，参数会作为单个表达式执行；不能直接传入由分号连接的多条语句。
需要先滚动或声明局部变量时，使用能够返回断言结果的 IIFE，或拆成多个 `eval` 命令。出现
`Unexpected token ';'` 时应先修正验证表达式并重跑同一视口，不能把验证器语法错误记成页面失败。
Playwright 驱动回调中的局部变量也不会自动进入 `page.evaluate` 的浏览器上下文；需要在页面内使用的数据
必须作为参数传入，或先分别取得两个上下文的结果再在驱动侧合并。出现 `ReferenceError` 时应修正上下文边界，
从当前视口重新执行整组页面断言，不能把探针作用域错误记成页面缺少内容。
当前 Playwright CLI 的 `run-code` 参数需要写成 `async (page) => { ... }` 回调源码；直接传入
`await page...` 或 `console.log(await page...)` 会在包装执行前产生语法错误。需要多步页面探针时，应让回调
返回结构化断言结果，并先用最小的 `async (page) => page.title()` 确认调用形状，再重跑目标视口。
页面继承全局 `scroll-behavior: smooth` 时，`window.scrollTo()` 返回后滚动动画可能尚未结束，立即读取
`scrollY`、元素位置或课程末尾会得到过渡中的假结果。末尾断言应先在临时会话中把滚动行为设为 `auto`，
或显式等待滚动完成后再读取同一组值；不能把 `atBottom: false` 直接记成正文没有渲染到末尾。
课程布局还可能让 `article`、侧栏等内部元素独立滚动，此时文档高度等于视口高度，`window` 的
`atBottom: true` 不能证明正文已经滚到末尾。应先枚举 `scrollHeight > clientHeight` 且纵向可滚动的元素，
对真实正文容器设置 `scrollTop = scrollHeight`，再同时核对该容器的底部位置、末尾文本和截图。
本仓库当前 Playwright CLI 使用 `requests`、`request` 等子命令查看网络记录，不支持旧参考中的 `network`；
静态模块默认被隐藏，需要 `requests --static` 才能列出。出现 `Unknown command: network` 时应先按当前 CLI
`--help` 修正验证命令，再继续定位真实页面问题，不能把工具版本差异记成课程页面错误。

当前 Playwright CLI 的 `screenshot` 位置参数表示元素引用或选择器，不是输出文件名。保存到指定文件必须使用
`--filename <name.png>`，需要整页时再加 `--full-page`；若把文件名写成位置参数并得到“does not match any
elements”，应先按 `screenshot --help` 修正命令并重跑，不能把参数错误记成页面截图失败。

从课程 Markdown 提取 Java 代码做临时编译验证时，必须按代码围栏或 Markdown AST 的实际边界提取，不能依赖
会随正文增删而漂移的固定行号。生成源码后先检查首尾是否仍为合法 Java；若编译器报告标题、说明文字或围栏
标记，先修正提取范围并从同一 JDK、同一正文副本重跑，不能把验证脚本混入的 Markdown 文本记成课程代码错误。

并行课程进行浏览器验收时，每课必须使用唯一的 Playwright 命名会话，不能共同复用 `default` 会话；每组
断言还要同时核对当前 URL 与 H1。若页面已被其他任务导航，当前组断言全部作废，应在本课命名会话中重新
打开目标 URL，并从桌面视口开始完整重跑，不能把其他页面的无溢出或无控制台错误当成本课证据。

使用 `playwright-cli` 验收时，从当前课程的独立 `/tmp` 目录执行命令，并使用目标页面的绝对 URL；不要在
仓库根目录运行而让 CLI 写入 `.playwright-cli` 快照、日志或截图。课程闭环后只删除本课新建的临时目录，
不得清理仓库中已有的浏览器产物或其他课程资产。

把独立 `/tmp` 目录作为命令 `workdir` 时，该目录必须在启动命令前已经存在；不能指望在同一条命令中先
`mkdir`，因为执行器会在 shell 运行前先解析并进入工作目录。出现 `CreateProcess` 的 `No such file or directory`
时，应先从已存在的目录创建目标目录，再从目标 URL 重跑完整浏览器反馈环，不能记成课程页面失败。

元数据也要先按 YAML 语法核对：来源标题、摘要等包含冒号的标量值使用引号包裹，避免 frontmatter 在
TypeScript 检查通过后才由 Markdown 构建阶段拒绝。

YAML frontmatter 中以 `@`、`!`、`&`、`*`、`{`、`[` 等保留字符开头的 claims、摘要或标题也必须使用引号；
来源标题中出现 `::` 等可能被解析为映射的冒号组合时同样引用整个标量。Prettier 通过不能证明 YAML 合法，
必须从真实 `*.md?content-entry` 路径重跑解析，确认错误发生在正文读取之前还是课程内容本身。

同一份源码需要使用多个 JDK 版本验证时，每个版本必须使用独立的源码副本或 class 输出目录，尤其不能
并行编译到同一目录。否则后完成的编译会覆盖前一个版本的产物，使旧版运行时误读新版 class 并报告
`UnsupportedClassVersionError`，从而把验证环境污染误判为课程代码不兼容。

涉及基本类型转换时，反馈环必须把“应编译失败”的片段和“应输出有损结果”的片段分开验证：前者核对
编译器确实拒绝不兼容赋值，后者核对截断、低位保留、浮点精度或 NaN/无穷大边界的实际输出。不能只
检查主程序能运行，就把强制转换写成“自动安全”的结论；同一转换的 JDK 25 与 Java 8 结果也必须在
独立输出目录中分别复现。

练习的约束、参考实现和预期输出必须三方对齐；当输入值刻意选择了大整数或有损转换边界时，不能把
“变量声明值”“转换后的输出”和验收文字写成不同数字。反馈环一旦发现这种矛盾，应先修正文档或代码
中的单一事实，再从相同命令重跑两个版本，不能用验证脚本迁就错误的期望值。

正文对实现采用的循环、API 或统计方式的描述必须与代码逐项对应；方法名和 Javadoc 必须准确表达实际
处理范围，不能用 `copyTwo` 命名一个会复制任意长度数组的方法。示例中来自同一业务事实的统计值也必须
自洽，例如“总数 - 已完成数”应等于列出的待处理数。复审发现不一致时，应同时修正讲解、命名、输入
数据和预期输出，并重跑两个 Java 版本的完整反馈环。

涉及索引区间时，正文、Javadoc 与实现必须使用一致的边界表示，例如循环条件为 `index < taskCount` 时，
已使用区间应写成 `[0, taskCount)`，不能写成会包含上界的 `0..taskCount`。校验方法还要在名称中区分
“文本格式合法”和“编号真实存在”；只检查字符形式的方法不能命名成已经确认任务存在。

示例需要展示首尾空白时，不能把空格直接留在 Markdown 代码行末或输出注释末尾；Prettier 可能接受这类
内容，但 `git diff --check` 会报告 trailing whitespace。应使用方括号等可见边界输出，例如
`System.out.println("[" + text + "]")`，同时运行格式检查和 `git diff --check`。

多文件 `apply_patch` 只要有一处上下文与 live 文件不一致，就可能在落盘前整体拒绝补丁。失败后应重新读取
每个目标的精确相邻行，并核对所有文件都没有部分修改，再把补丁缩到最小上下文重试；不能继续沿用旧快照，
也不能把补丁校验失败误记为课程或构建失败。

同一篇 Markdown 含有多个结构相似的完整代码块时，只用一行 `import` 等短上下文执行 `apply_patch`，可能
命中较早的版本代码块，造成一个代码块重复导入、另一个仍缺少导入。修改双版本程序时应把课程小节标题、
类名或其他唯一相邻内容纳入补丁上下文；落盘后立即定向统计相关导入，并重新从代码围栏提取、编译两个版本。
Prettier 通过不能证明导入完整或唯一，不能用格式检查代替编译反馈环。
