# 课程内容规范

> 版本：v2.5
> 日期：2026-08-19
> 状态：生效
> 适用范围：`src/categories/frontend/<technology>/<module>/learn/`

## 1. 课程职责

课程负责建立心智模型、学习顺序和可完成练习，不承担完整官方索引速查。每课只讲解一个可以独立
命名的核心知识点，标题、slug、稳定 ID 和主要学习目标必须指向该知识点。关联能力可以短暂说明并
链接对应课程，不能在当前课程展开第二个完整知识点。

课程必须围绕知识点本身组织，从零基础定义进入意义、语法、常规用法、易错点、进阶用法与适用边界。
不得用综合项目的操作步骤替代知识解释；跟做步骤只能用于练习或整合已经完成的知识点。

课程内容以本科阶段常用前端开发能力为边界。属于本课知识点的必要内容应尽量完整覆盖，不设置正文
行数或字数上限；语言保持直接、准确，删除不提供新信息的铺垫、重复结论和修饰语。课程正文只描述
本课知识，不出现计划编号、批次、进度、下一课安排或其他课程的实施过程。

课程按基础、中级、高级等阶段组织，但真实顺序由前置关系和 module manifest 决定。阶段只用于模块
总览分组和学习路径，不进入文件必选层级或 URL。

## 2. 文件与元数据

```text
src/categories/frontend/<technology>/<module>/learn/<slug>.md
src/categories/frontend/<technology>/<module>/demos/<demo-slug>/...
```

课程正文统一使用 Markdown。每个 Module 的 `manifest.ts` 显式登记条目、slug、stage、顺序和 loader，
页面不得扫描目录推断课程。

| 字段 | 规则 |
| --- | --- |
| `id` | 全局稳定，移动文件时保留现有值，必须与 manifest 一致 |
| `type` | 固定为 `lesson` |
| `title` | 简短、可识别的知识点名称，不使用计划编号、“第一章”等顺序词或冗长说明 |
| `summary` | 一句话说明学完能解决什么问题 |
| `domain` | 固定为 `frontend` |
| `technology/module` | 与所属 Technology、Module manifest 一致 |
| `stage` | 学习阶段标识，只用于分组和排序 |
| `level` | `beginner`、`intermediate` 或 `advanced` |
| `prerequisites` | 真实前置课程 ID；没有时为空数组 |
| `related` | 已上线的相关课程和 Reference ID |
| `tags` | 稳定检索词，不堆叠无意义同义词 |
| `sources` | 实际支持正文结论的一手来源 |
| `appliesTo` | 精确适用版本或版本范围 |
| `verifiedAt` | 本批真实核验日期 |
| `estimatedMinutes` | 与内容和练习规模相符的估算 |

课程计划不写死教学技术的具体版本。每篇课程开始编写时重新查询当时最新稳定版，排除 beta、rc、
canary、experimental 等预发布通道，再把本课实际核验的版本写入 `appliesTo`、`verifiedAt` 和来源。
不得因为计划制定时间较早而沿用当时版本，也不得用本地已安装版本替代最新稳定版。

课程正文只解释当前知识点对应的公共规则；仓库本地依赖版本、宿主兼容情况、临时验证方式和升级条件
只在当次调研与验证中使用，不写入课程正文。只有版本差异本身直接改变当前知识点的公共用法时，正文
才说明该差异。

## 3. 固定内容顺序

课程按以下节奏编写：

1. 学习目标：提供可验证目标。
2. 为什么需要：用学习者已经理解的场景引出问题。
3. 核心概念：最小模型、语法或 interface。
4. 用法与示例：解释常规写法、结果和使用条件，再逐渐进入进阶用法。
5. 用法示例或 Demo：帮助学习者观察当前知识点；组合 Demo 可以复用多个强相关知识点。
6. 易错使用提示：使用受控 `pitfalls` directive。
7. 源码推导与适用场景：区分官方事实、课程推导和使用边界。
8. 练习：要求学习者修改、预测结果或解释原因。
9. 本节小结：只保留可带走的判断规则。
10. 参考资料：列出实际支撑正文的一手来源。

章节可以按主题增加，但不能删掉目标、易错提示、推导/场景、练习、小结和参考资料。没有浏览器
可观察价值的知识点直接使用最小代码示例解释，不得为了形式强行创建动画或把临时验证过程写入正文。

正文唯一的一级标题不编号。根级二级标题按文档内出现顺序使用 `一、`、`二、`、`三、`，根级三级
标题在每个二级标题下使用 `1.`、`2.`、`3.`，遇到新的二级标题后重新从 `1.` 计数。序号直接写入
Markdown 标题内容；代码块和 `pitfalls`、`exercise` 等 directive 内部的结构化标题不参与编号。

面向学习者的正文不得出现临时 fixture、`/tmp` 路径、本地依赖版本、仓库命令、构建结果、源码哈希、
浏览器验收数据、Gate 状态、复审结论、课程计划或完成进度。TypeScript、构建工具和浏览器规则只有
直接构成当前知识点的公共合同，才可以进入正文。

每篇课程编写前只实时调研当前知识点，不建立独立调研文档。当前知识点完成调研、正文、临时验证、
适用时的浏览器验证、按风险复审并勾选模块课程计划后，才能开始下一篇；不得一次性预调研或预写
整批课程。实际支撑正文的关键官方来源必须进入课程 `sources` 和参考资料。

技术独有的代码形式、运行宿主和生态边界写入对应技术补充规范。补充规范只能增加该技术所需的差异
规则，不能覆盖或放宽本规范。

## 4. 易错提示与推导

每个易错点包含错误名称、触发条件、原因、后果、错误示例、正确示例和验证方式。通常选择约五个
高价值错误，最多十个；不得把同一个问题拆成多个条目凑数。

“源码推导与适用场景”先写固定版本源码或官方测试证明的事实，再写课程层面的推导和使用边界；
不得把内部实现描述成公共承诺。没有源码价值的语言规则可以改为“原理与适用场景”，但仍需绑定
规范或官方编译行为。

需要本地 Demo 时使用 `:::demo{id="完整稳定 Demo ID"}`；该 ID 必须在同一 Module manifest 中登记。
一个 Demo 可以被多篇相关课程复用，但每篇课程仍须独立完成本知识点的定义、用法、易错点和边界。

## 6. 发布检查

- manifest 中的前置、顺序、stage、slug 和状态与正文一致。
- 目标、总结、易错点和推导章节满足 Markdown schema 与模板测试。
- 根级二级、三级标题序号连续且符合父子层级，directive 内部标题没有被误编号。
- 本课使用的 Demo 已可运行；组合 Demo 明确覆盖的知识点与每个观察目标。
- 临时验证、本地环境和验收结果没有进入课程正文。
- 模块课程计划只勾选本课复选框，没有追加调研、验证、复审或逐课执行日志。
- 维护现有课程时不静默改变范围、顺序或正文结论。
- 桌面和 390px 可完成阅读、目录切换、练习与相关跳转。
- 新路径可刷新，稳定 ID 对应的进度保留，旧路径不重定向。
